# Serial transport implementation / offline tests

`serial_transport.py` SHA `5060e1922aeeac7de932da317318c3f170941b397483c7702f9b2f3748a4e146` implements exact ordered HELLO then 1,024 requests with input validation before enumeration/open. `SerialExchange` receives read/write callbacks with remaining timeout and a durable-retention callback. It preserves every request before writing and every returned read chunk before validating deadlines/framing/CRC/identity. One application write per request; partial/ambiguous write, empty read, bad response, retention failure or deadline failure poisons the instance without retry. Prefix resynchronization is bounded and HELLO-only. No reset/flush/recovery command is added.

`open_exact_esp` requires explicit port plus unique exact serial, VID 303a / PID 1001, allowing a by-id path to resolve to the matching canonical tty. It uses Serial(None), configures DTR/RTS False before open, requests advisory exclusivity then TIOCEXCL, and rechecks device metadata before yielding. Failure after construction attempts close; leaving the context poisons the transport. Neither enumeration nor HELLO proves physical module SKU, programmed image/readback or electrical state.

Actual offline tests `a53d48`/0: **23 PASS**, 0.12 s, 4 GiB/swap0 scope; see `SERIAL_TRANSPORT_TEST_EXECUTION.json` for exact source/test/XML and invocation bindings. Synthetic controls include all 1,024 fragmented responses, retained HELLO noise, exact noise bound, no inference resynchronization, before/after deadlines including late callback returns, ambiguous/partial write, CRC failure, retention failure, invalid last input before enumeration, duplicate/wrong USB identity, changed identity after open, exclusive failure and closure. Provider seams are explicit; no USB or serial calls occurred. The initial 22-pass/1-fail run is retained and led only to the binary64 remaining-time clamp, not a protocol, tolerance or physical-policy change.

The 10-second exchange bound and 4,096-byte noise allowance are host engineering policies, not electrical or MCU execution limits. Blocking OS/driver open/close calls still need an outer process deadline. Ordinary pySerial POSIX open discards pre-existing input; only returned post-open bytes are claimed retained. The official [pySerial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html) also warns that drivers may transiently assert DTR/RTS on open and may ignore certain POSIX line-setting errors. No no-glitch, no-reset electrical guarantee is made. TIOCEXCL is not proof that a prior/privileged owner cannot interfere. Tests do not validate real device timing, firmware behavior or power safety.
