# N6 bench — SRAM-vs-flash experiment protocol (pre-registered 2026-09-18)

## Hypothesis under test

H1: the v3 STM32N6 latencies (0.29–0.46 ms for the ~105–120 k-MAC IDS MLPs on the NPU,
1.23–1.24 ms for FP32 on the M55) are bound by streaming the weights from the external
octo-SPI NOR flash (XSPI2, 0x70000000), not by compute. Evidence in the v3 numbers: every
model implies 280–410 MB/s of weight bytes per unit time; the NPU at 600 GOPS would need
~0.4 µs for the same MACs.

Prediction if H1 holds: with the same kernel and the same bytes, moving the weights from
XSPI2 flash to on-chip AXI SRAM reduces latency by roughly (flash bytes/s)/(SRAM bytes/s),
i.e. several-fold to >10×; the compute-only floor (weights in SRAM, caches on) is far below
the v3 latencies. Prediction if H1 fails: SRAM vs flash placement changes latency by <20 %
(as on the RA4E1, where the M33 CMSIS-NN kernel is compute-bound: 10.7 % gain).

Scope of *this* phase (Phase A, CPU only): the Neural-ART path needs ST Edge AI Core
output (blocked on the st.com download), so Phase A measures the Cortex-M55 side —
CMSIS-NN INT8 (Helium MVE) and a plain scalar FP32 loop — with weights at the two
placements. It tests the bandwidth mechanism directly (read-bandwidth probes) and the
CPU-path prediction; the NPU-path prediction is Phase B with the same harness.

## Controls

- Same binary, same kernel, same dims, same iteration count; only the weight base address
  differs (SRAM2 at 0x34100000 vs XSPI2 at 0x70000000 + 1 MB). Biases, activations and
  kernel sums always in SRAM.
- Interrupts masked, SysTick off, MPU disabled (architectural default map), LTDC stopped
  (only if it was clocked), caches explicitly set per condition: off / on-cold
  (clean+invalidate before every iteration) / on-warm.
- FPSCR FZ+DN set so FP32 timing does not depend on the (arbitrary) flash contents.
- Timing = DWT CYCCNT with DSB/ISB fences; overhead measured (CMD_NOP) and reported.
- 100 iterations per condition; report min / median / max / SD. Deterministic kernels are
  expected to repeat to within a few cycles (as on the RA4E1, ±1 cycle).
- CPU clock: decoded from RCC by the HAL (`HAL_RCC_GetCpuClockFreq`) AND measured on the
  host (DWT cycles vs wall clock over 3×2 s); both are reported and must agree to <0.5 %.
- XSPI2 configuration (prescaler, data lines, DTR) is captured from the live registers so
  the theoretical interface bandwidth can be stated next to the measured one.
- The OOB firmware's clock tree is inherited (documented), not reconfigured.

## Known limitations (stated up front)

- CPU-issued reads are not NPU DMA bursts: with caches off each 32-bit load is one AXI
  transaction, so flash "bandwidth" seen by the core is a lower bound; cache-on-cold
  measures 32-byte line fills, closer to burst behaviour. The NPU stream engines will do
  better than either. Phase B measures the NPU itself.
- The FP32 loop is deliberately naive (scalar; GCC does not vectorise the float reduction
  without -ffast-math); it is not ST's optimised FP32 runtime.
- The flash region holds the OOB image, i.e. arbitrary bytes; INT8 timing is data
  independent, FP32 timing is made data independent by FZ/DN.
- Whole-image, single-board, single-session; the board's XSPI clock is whatever the OOB
  FSBL configured, which may differ from the ST cloud benchmark firmware.
